# DocMind

Ask questions about your own documents and get answers with citations. A small retrieval-augmented generation (RAG) app in TypeScript: Node/Express API, React frontend, and a retrieval eval harness.

It runs fully offline by default. Add an Anthropic API key and answers are generated by Claude instead.

## Features

- Upload `.txt` / `.md` files; they are chunked, embedded and stored
- Ask questions; answers cite numbered sources you can click through to
- **Abstains instead of guessing**: if nothing relevant is retrieved, the LLM is never called
- Pluggable embedder and LLM behind small interfaces
- Input validation (zod), per-IP rate limiting, atomic on-disk persistence
- Unit and API tests, plus a retrieval eval with pass/fail quality gates

## Quick start

```bash
npm install
npm run dev:server        # API on :3001
npm run dev:web           # UI on :5173 (proxies /api to :3001)
```

Open http://localhost:5173 and upload the files in `server/eval/corpus/` to try it.

To use Claude for answers:

```bash
ANTHROPIC_API_KEY=sk-ant-... npm run dev:server
# optional: ANTHROPIC_MODEL=claude-sonnet-5-5 (default)
```

Other scripts:

```bash
npm test            # vitest: chunker, embedder, store, API
npm run eval        # retrieval quality; exits non-zero below the gates
npm run typecheck   # server + web
npm run build       # production build of the frontend
```

## How it works

```
upload ──► chunker ──► embedder ──► vector store (JSON on disk)
                                         │
question ──► embedder ──► cosine search ─┘
                              │
                 drop hits below minScore
                              │
              none left? ──► "couldn't find that" (no LLM call)
                              │
                 numbered passages ──► LLM ──► answer with [n] citations
```

| File | Responsibility |
|---|---|
| `server/src/chunker.ts` | Sentence-aware chunking with overlap |
| `server/src/embedder.ts` | `Embedder` interface + offline `HashEmbedder` baseline |
| `server/src/vectorStore.ts` | Brute-force cosine search, atomic JSON persistence |
| `server/src/llm.ts` | `LLM` interface, `ExtractiveLLM` (offline), `AnthropicLLM` |
| `server/src/rag.ts` | Ingest and ask orchestration, abstain guardrail |
| `server/src/app.ts` | HTTP API, validation, error handling |
| `server/eval/` | Golden questions, corpus, eval runner |

## Design decisions and trade-offs

- **Offline baseline embedder.** `HashEmbedder` uses signed feature hashing over unigrams and bigrams. It matches on shared vocabulary, not meaning, so "car" will not match "automobile". It keeps the project runnable and testable with no keys or downloads. For real semantic search, implement `Embedder` with a neural embedding model.
- **Abstain over hallucinate.** A score threshold (`minScore`, default 0.12) gates the LLM call. It trades some recall for never answering from irrelevant context. The threshold was set by hand and is the most fragile number in the system; see the eval notes below.
- **Extractive fallback.** Without an API key, answers are the best-matching sentences from the retrieved passages. It cannot hallucinate, but it also cannot combine information across passages.
- **Prompt-injection posture.** Uploaded documents are untrusted. The system prompt tells the model to treat passages as data and ignore instructions inside them. That reduces the risk but does not eliminate it.
- **Brute-force search.** Scanning every chunk is O(chunks x dimensions). Fine for thousands of chunks; beyond that, use an ANN index (pgvector, HNSW).
- **JSON file persistence.** Written to a temp file and renamed so a crash cannot leave a torn file. It is single-process and rewrites the whole file on every change. A database is the next step.
- **In-memory rate limiter.** Correct for one instance. Multiple instances need shared counters (for example Redis).
- **Client-side file reading.** The browser reads text files and posts JSON, which avoids multipart handling. PDF and DOCX would need server-side parsing.

## Evaluation

`npm run eval` ingests `server/eval/corpus/` and runs `server/eval/golden.json`:

- **hit@k**: does the expected document appear in the top k chunks?
- **MRR**: how high does the first correct chunk rank?
- **abstain**: are unanswerable questions rejected by the threshold?

Current baseline: hit@1 100%, hit@3 100%, MRR 1.00, abstain 100% (10 answerable, 3 unanswerable questions).

Read that number with care. The set is small and hand-written, the corpus has five very distinct topics, and the lexical embedder has an easy job. The weakest case ("What is an ETag used for?") scores 0.13 against a 0.12 threshold, so it only just passes. A harder corpus with overlapping topics and paraphrased questions is the first thing to add.

## Limitations and next steps

- Swap in a neural embedder and compare it against the baseline using the eval harness
- Grow the golden set (overlapping topics, paraphrases, multi-chunk answers) and report it per category
- Hybrid retrieval (BM25 plus embeddings) and reranking
- PDF and DOCX ingestion
- Streaming answers, conversation history, per-user document collections with auth
- Replace the JSON store with Postgres and pgvector; add Dockerfile and CI
